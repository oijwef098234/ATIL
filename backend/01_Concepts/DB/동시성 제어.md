## 동시성 제어란?

> 여러 사용자가 동시에 같은 데이터를 건드릴 때 데이터가 안 깨지게 통제하는 모든 방법

- 여러 방법이 있다.
- 비관적 락, 낙관적 락

---

## 비관적 락이란?

> 무조건 에러가 발생한다는 가정 하에 미리 DB 차원에서 막아두는 것

### 특징

- 트렌젝션 시작과 동시에 DB에 락이 걸림
- 안전하지만 느리다.

### 언제쓰냐?

- 에러가 발생하면 안되는 경우 ex) 돈, 제고 같은 경우

### 예시 코드

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select u from User u where u.id = :id")
User findByIdForUpdate(Long id);
```

- 여기서 `@Lock(LockModeType.PESSIMISTIC_WRITE)` 이 부분이 락을 거는 부분임
- 수정되어 트렌젝션이 완료되기 전까지 다른 트렌젝션 대기

---

## 낙관적 락이란?

> 거의 에러가 발생하지 않는다는 가정, 에러가 발생하면 그때 가서 처리함

### 특징

- 버전 단위로 감시한다.
- 충돌 발생시 예외처리를 통해 해결해야한다.

### 언제쓰냐?

- 읽기 많고 수정 적은 서비스
- 게시글 수정
- 프로필 수정
- 대부분의 일반 CRUD

---

### 버전 단위로 감시한다? 무슨말일까

엔티티 상태가 이렇다고 치자.

```
값(value) = 3
버전(version) = 1
```

### A 라는 유저가 조회함

```
value = 3
version = 1
```

### B 라는 유저도 조회함

```
value = 3
version = 1
```

### B 가 먼저 수정

B가 3 → 2로 수정하고 저장함.

이때 JPA가 날리는 SQL은 대충 이거임

```sql
UPDATE table
SET value = 2,
    version = version + 1
WHERE id= ? 
		AND version=1;
```

- 조건 만족
- row 1개 수정
- version = 2 됨

DB 상태:

```
value = 2
version = 2
```

---

### A 도 수정 시도

너도 **자기는 아직 version=1이라고 믿고** 저장을 시도한다.

JPA가 또 이 SQL을 날린다.

```sql
UPDATE table 
SET value = 2,
    version= version+1
WHERE id= ?
		AND version=1;
```

근데 지금 DB는?

```
version = 2
```
